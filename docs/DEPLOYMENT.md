# Deploying NachCareAI to Render (public demo/staging)

**This is a public demo/staging deployment, not a production system cleared
for real patient use.** No real patient data should ever be entered here —
consent texts, escalation thresholds, and knowledge-base content are all
`PLACEHOLDER_CLINICAL` (see `docs/OPEN_CLINICAL_ITEMS.md`), and several
legal/DPA prerequisites for real use are still open (`docs/OPEN_DECISIONS.md`
#1, #4, #6, #7, #8, #14). Treat everything here as demo-quality, not
clinical-quality.

This runbook is for the product owner (or anyone with access to the
`NanaSaha/NachCare` GitHub repo) to actually deploy what's already been
prepared in this repo. It assumes no prior Render account.

See `docs/adr/0015-render-demo-deployment.md` for *why* each choice below
was made. **Nothing in this document has been tested against a real Render
account or a real Blueprint sync** — it was written by reading Render's
current documentation and hand-checking `render.yaml` against it, not by
actually deploying. Treat your first attempt as the real test of this
guide, and expect to hit at least one thing that needs a small fix.

---

## 0. What's already done for you

Everything in this repo is ready to deploy as-is:

- `backend/Dockerfile.production` — production Rails image, built and
  boot-tested locally (see "What was verified locally" below).
- `render.yaml` — a Render Blueprint defining all 4 services + 1
  database, entirely on free instance types (ADR-0016).
- Angular production builds wired (`frontend/angular.json`
  `fileReplacements`) to point at the real deployed backend URL instead of
  `localhost:3001`.
- A fresh production VAPID (Web Push) keypair generated — the public half
  is already committed; the private half is in a gitignored local file,
  see step 3.

You do not need to write any code or run any local commands to deploy —
just follow the steps below in Render's web UI.

---

## 1. Create a Render account

1. Go to <https://render.com> and sign up (GitHub sign-in is simplest —
   it also handles step 2 for you).
2. If you didn't sign up with GitHub, connect your GitHub account under
   **Account Settings -> Connected Accounts** and grant Render access to
   the `NanaSaha/NachCare` repository (or all repos, your choice).

## 2. Create the Blueprint

1. In the Render dashboard, click **New -> Blueprint**.
2. Select the `NanaSaha/NachCare` repo, branch `main`.
3. Render finds `render.yaml` at the repo root automatically and shows a
   preview of the 4 services + 1 database it's about to create, all on
   free instance types (see `docs/adr/0016-free-tier-render-deployment.md`
   for why this is 4 services, not the 6 an earlier version of this file
   described):
   - `nachcare-backend` (web, Docker, Frankfurt) — runs both Puma *and*
     Sidekiq in one process (`bin/render-web-with-sidekiq`); Render has no
     free instance type for a separate background worker service
   - `nachcare-caregiver` (static site — the caregiver PWA)
   - `nachcare-cockpit` (static site — the clinical cockpit)
   - `nachcare-redis` (Key Value, Frankfurt)
   - `nachcare-db` (Postgres, Frankfurt)
4. Give the Blueprint a name (e.g. "nachcare-demo") when prompted.

## 3. Set the one secret Render can't generate for you: `VAPID_PRIVATE_KEY`

Render will pause and ask you to fill in any env var marked `sync: false`
in `render.yaml` — there is exactly one: `VAPID_PRIVATE_KEY` on the
`nachcare-backend` service (via the shared `nachcare-shared` env var
group).

The value is in a file on disk in this repo checkout, **not committed to
git** (gitignored on purpose — see `docs/adr/0015-*.md` for why this one
key couldn't just be Render-generated like all the others):

```
ops/vapid_production_key.local.txt
```

Open it, copy the `VAPID_PRIVATE_KEY` value, and paste it into Render's
prompt. (The matching public key is already baked into the caregiver
PWA's build — you don't need to enter that one anywhere; it's a plain
`value:` in `render.yaml` already.)

Every other secret (`SECRET_KEY_BASE`, the three
`ACTIVE_RECORD_ENCRYPTION_*` keys, `CAREGIVER_DEVICE_TOKEN_PEPPER`,
`CAREGIVER_PIN_PEPPER`) is generated by Render itself at this point —
you won't be asked for those.

## 4. Deploy

Click **Apply** (or **Create New Resources**, wording may vary by Render
UI version). Render will:

1. Create the Postgres database and Key Value instance first.
2. Build `nachcare-backend`'s Docker image from
   `backend/Dockerfile.production`.
3. Run `nachcare-backend`'s `preDeployCommand`
   (`bin/rails db:prepare && bin/rails db:seed`) — creates the schema and
   loads the drug list / escalation ruleset / knowledge base / Learn
   content (all idempotent, safe to run again on every future deploy).
4. Build both static sites (`npm ci && npx ng build <project>
   --configuration production` in `frontend/`).
5. Start `nachcare-backend` via `bin/render-web-with-sidekiq`, which runs
   Puma and Sidekiq (loads `config/schedule.yml`'s cron jobs on boot) as
   two processes inside the one container — see
   `docs/adr/0016-free-tier-render-deployment.md` for why they're merged
   instead of separate services.

First deploy will likely take several minutes (the Docker image build is
the slow part). Watch the service's **Logs** tab in the Render dashboard.

**Free-tier behavior to expect, not a bug:** `nachcare-backend` spins down
after 15 minutes with no inbound traffic (Render's free web service
limit) and cold-starts on the next request — this also pauses Sidekiq
(and `schedule.yml`'s cron jobs) for as long as it's spun down, since
they're the same process. A demo that gets visited regularly stays warm;
one that sits idle for hours will have a slow first request and may have
missed a scheduled job tick in the meantime. See ADR-0016 if this becomes
a real problem — the fix is reverting to a separate paid Sidekiq worker.

**Known gap in this step, unverified:** whether `preDeployCommand` behaves
exactly as documented for `runtime: docker` services was not something
this preparation work could test without a real account — if the backend
service fails to come up, check its logs for a migration error first.

## 5. One-time step: enable the `pgvector` Postgres extension

The app's AI-retrieval feature (RAG over `knowledge_chunks`) needs the
`vector` Postgres extension, and `render.yaml`'s `databases` schema has no
field to declare extensions (checked against Render's current Blueprint
docs — no such key exists). This is a one-time manual step after the
database first exists:

1. Open `nachcare-db` in the Render dashboard -> **Connect** tab.
2. Use the **PSQL Command** shown there (or Render's browser-based psql
   console if offered) to connect.
3. Run:
   ```sql
   CREATE EXTENSION IF NOT EXISTS vector;
   ```
4. Confirm it worked: `\dx` should list `vector` in the extension list.

Render's own docs/community posts (checked while preparing this repo,
not assumed) say pgvector is available for new Render Postgres databases;
if the `CREATE EXTENSION` command fails on your instance, contact Render
support (support@render.com) — this is the one thing in this whole guide
this preparation work genuinely could not test end-to-end.

Do this **before** `nachcare-backend`'s first `db:prepare` runs if
possible (i.e., right after the database is created, before the Blueprint
finishes deploying the web service) — if a migration that uses `vector`
columns runs before the extension exists, it will fail and you'll need to
retry the deploy after creating the extension.

## 6. Verify the deployment worked

### Health check

```
curl https://nachcare-backend.onrender.com/up
```
Expect `200 OK` (Rails' built-in health check — boots with no exceptions,
no DB dependency).

### Smoke-test checklist (mirrors this project's manual verification pattern)

1. **Cockpit loads**: open `https://nachcare-cockpit.onrender.com` — login
   screen renders.
2. **Nurse/admin login**: if you ran the Ingrid demo seed (step 7 below),
   log in as `sabine.demo.nurse@example.eu` — see that step for the
   password. Otherwise, no staff users exist yet; you'll need to create
   one (e.g. via a one-off `bin/rails runner` in the backend's Shell tab)
   before you can log into the cockpit at all.
3. **Ward nurse enrolls a patient**: cockpit -> Enrollment -> fill the
   form -> get an activation code + printable A5 sheet (PDF should
   download/render).
4. **Caregiver activates**: open `https://nachcare-caregiver.onrender.com`
   on a phone-width browser window, enter the activation code, complete
   onboarding (language, consents, PIN).
5. **Caregiver submits a check-in**: weight, medications, symptoms, note
   — confirm it submits successfully and the caregiver sees a result
   screen.
6. **Escalation shows up in the cockpit**: if the check-in you submitted
   should trigger a flag (e.g. a large weight jump, or use the seeded
   Ingrid scenario's day-17 data), confirm it appears in the cockpit's
   triage queue, ideally live via ActionCable (open the cockpit queue in
   one tab, submit a check-in in another, watch it appear without a
   manual refresh — this exercises `REDIS_URL`/ActionCable wiring, not
   just HTTP).
7. **AI-adjacent screens degrade visibly, not silently**: open the
   caregiver assistant chat and ask a question. With no
   `ANTHROPIC_API_KEY`/`GEMINI_API_KEY`/AWS/Azure credentials set (the
   deliberate default — see section 8 below), expect the assistant to
   route to the nurse (not answer), and the AI-drafted brief/triage-note
   panels to either show template-only text or hide themselves — **not**
   an error page. If you see a raw error instead of a graceful
   degradation state, that's a real bug worth reporting, not expected
   behavior.
8. **Emergency block always renders**: the static 112 emergency guidance
   on any alert screen / Care-team page should render even if you
   simulate the backend being down (R4) — spot-check this once.

## 7. Optional one-off: seed the full Ingrid/Sabine demo scenario

`db/seeds/ingrid_scenario.rb` reproduces the complete demo story used
throughout this project's own manual verification — a 90-day episode, a
day-17 RED flag with a real nurse "save" (intervention), and two staff
logins — driven through the real escalation pipeline, not hand-crafted
rows. It is **not** run automatically by the deploy (see
`docs/adr/0015-*.md` section 3 for why) because it creates a nurse and
site-admin login with a fixed, publicly-known password:

```
email:    sabine.demo.nurse@example.eu       (role: nurse)
email:    sabine.demo.admin@example.eu       (role: site_admin)
password: correct horse battery staple
```

If you want this seeded (recommended for actually demoing the product —
otherwise there's no staff login to test the cockpit with, and no
pre-built RED flag to show):

1. Open `nachcare-backend` in the Render dashboard -> **Shell** tab.
2. Run:
   ```
   bin/rails runner db/seeds/ingrid_scenario.rb
   ```
3. It's idempotent (checks for an existing patient with pseudonym code
   `PT-INGRID-DEMO` first) — safe to run more than once, it'll just print
   the existing IDs back if already seeded.

**Because this is a public URL**, that password is effectively public the
moment you run this. That's an acceptable tradeoff for a demo whose whole
purpose is to be shown to people, but it's your call, not a default this
deployment silently made for you — if you'd rather have a real, private
staff login, create one directly instead (same Shell tab):

```ruby
bin/rails runner 'User.create!(email: "you@example.com", password: "a-real-password", password_confirmation: "a-real-password", role: "site_admin", site: Site.first || Site.create!(name: "Demo Site", timezone: "Europe/Berlin"))'
```

## 8. AI provider keys — deliberately left unset

`ANTHROPIC_API_KEY` and `GEMINI_API_KEY` are **not** part of this
deployment's `render.yaml`, on purpose:

- They're documented (ADR-0014, `docs/SUBPROCESSORS.md`) as a **dev-only,
  explicitly non-EU exception** to this project's EU-only externals rule
  (R8) — `api.anthropic.com` and `generativelanguage.googleapis.com` have
  no EU region.
- `config/ai.yml`'s `production:` block was never built to use them
  anyway (it only recognizes `bedrock_anthropic`/`azure_openai`, both of
  which need real EU-hosted credentials this project doesn't have —
  `docs/OPEN_DECISIONS.md` #6).

**Result with no AI credentials configured at all** (this deployment's
default): the assistant routes every question to the nurse instead of
answering, AI-drafted briefs fall back to template-only text, and
AI-drafted triage/call notes simply don't show a draft panel. This is
real, tested, documented behavior
(`Domain::Ai::Gateway#call!`/`AllProvidersFailed`, see ADR-0015 section 8)
— not a crash, not a stub answering under the hood. If you want to
demo *real* AI responses on this deployment, you have two options, in
order of how consistent they are with this project's own rules:

- **Consistent with R8, but needs real (currently nonexistent) EU
  credentials**: set `AWS_REGION=eu-central-1` +
  `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` (Bedrock) and/or
  `AZURE_OPENAI_ENDPOINT`/`AZURE_OPENAI_DEPLOYMENT`/`AZURE_OPENAI_KEY` as
  extra env vars on `nachcare-backend` once you have real EU-hosted
  accounts for either.
- **Same deliberate, documented R8 exception this project already made
  for local dev (ADR-0014)**: add `ANTHROPIC_API_KEY` or `GEMINI_API_KEY`
  as an env var and set `AI_PROVIDER_OVERRIDE=anthropic` or `=gemini`.
  This is a conscious call for you to make for a *public* deployment, not
  a default — think about it the same way ADR-0014 framed it for dev
  before doing this.

## 9. Cost overview (as configured in `render.yaml` today)

This deployment is **$0/month as configured** — see
`docs/adr/0016-free-tier-render-deployment.md` for the trade-offs this
required (no persistent disk, Sidekiq merged into the web process, and
the free-tier spin-down behavior described in step 4 above).

| Service | Plan | Why | Approx. cost |
|---|---|---|---|
| `nachcare-backend` | `free` | Runs Puma + Sidekiq in one process (ADR-0016) — no separate paid worker needed, no persistent disk | $0 |
| `nachcare-db` | `free` | Kept free by default so this deployment doesn't impose a recurring cost decision for you — **but see the callout below** | $0, for 30 days |
| `nachcare-redis` | `free` | Demo-scope Sidekiq queue/ActionCable pubsub; data loss on restart is a minor inconvenience here, not a real risk | $0 |
| `nachcare-caregiver` / `nachcare-cockpit` | (static, no plan field) | Static sites are always free on Render | $0 |

**If you'd rather pay ~$14/month for a closer-to-production setup**
(persistent disk for check-in photos, a real always-on Sidekiq worker, no
15-minute spin-down): revert `nachcare-backend` to `plan: starter`, add
back its `disk:` block, change `dockerCommand` back to the default
(remove the line entirely), and re-add a separate `nachcare-sidekiq`
worker service — see ADR-0016 for the exact shape this had before the
free-tier redesign (or `git log -p render.yaml` for the literal diff).

**Important: `nachcare-db`'s free Postgres plan expires 30 days after
creation** (14-day grace period, then the database and all its data are
deleted — confirmed via Render's changelog, not assumed). If you want
this demo to outlive 30 days, change one line in `render.yaml` before or
after the first deploy:

```yaml
databases:
  - name: nachcare-db
    plan: basic-256mb   # was: free
```
and push/redeploy. Render will prompt you to migrate the data when you
change plans on an existing database — follow its prompts rather than
recreating the database from scratch (you'd lose all seeded/demo data
otherwise).

## 10. Redeploying after future code changes

Render auto-deploys on every push to `main` by default (configurable per
service in the dashboard under **Settings -> Auto-Deploy**). Each deploy
re-runs `nachcare-backend`'s `preDeployCommand`
(`db:prepare && db:seed`), which is safe/idempotent.

## What was verified locally vs. what's only documented

**Verified directly, with real commands, before this was committed:**

- `docker build -f backend/Dockerfile.production backend/` succeeds
  (multi-stage build, final image ~689MB).
- The built image boots Rails in `RAILS_ENV=production`
  (`bin/rails runner "puts 'boot ok'"` with a throwaway
  `SECRET_KEY_BASE`/encryption keys, no live database — confirms config
  loads, not that DB connectivity works, which needs a real Postgres).
- The built image runs as a non-root user (`docker run --rm <image>
  whoami` → `rails`, `id` → uid=1000/gid=1000).
- `npx ng build caregiver --configuration production` and `npx ng build
  cockpit --configuration production` both succeed; output confirmed at
  `frontend/dist/<project>/browser` (not `dist/<project>` directly — the
  Angular application builder nests a `browser/` subdirectory); the
  caregiver bundle was grepped to confirm the production `apiOrigin`
  (`nachcare-backend.onrender.com`) was actually baked in, not the dev
  `localhost:3001` value.
- Full backend test suite + rubocop re-run inside the existing dev Docker
  container after the `database.yml` production-block change: **616
  examples, 0 failures; 392 files inspected, no offenses**.
- `render.yaml` validates against Render's actual published JSON Schema
  (`render.com/schema/render.yaml.json`, checked programmatically with
  `jsonschema`, not just hand-read against docs) — this caught three real
  errors an earlier revision had (`envVarGroups` isn't a valid service
  key, `headers` had the wrong shape, `ipAllowList` is required on
  `keyvalue` services) that hand-checking against doc prose had missed or
  gotten backwards.
- `bin/render-web-with-sidekiq` (the script that runs Puma + Sidekiq in
  one container for the free-tier deploy, ADR-0016) was built into the
  production image and run against the real dev Postgres/Redis
  containers: both processes came up (confirmed via the boot logs and a
  `/up` health check), and `docker stop` shut both down cleanly within
  its grace period — no force-kill needed, confirming the SIGTERM
  trap/forward logic actually works, not just reads correctly.

**Not verified — genuinely requires a real Render account, out of scope
for this preparation work:**

- Whether the Blueprint actually syncs without errors on Render's real
  infrastructure.
- Whether `fromDatabase`/`fromService` env var wiring resolves exactly as
  documented.
- Whether `preDeployCommand` behaves as documented for `runtime: docker`
  services specifically.
- Whether `CREATE EXTENSION vector;` succeeds on a real Render Postgres
  instance (Render's docs say pgvector is supported; this wasn't tested
  against a live instance).
- Real network behavior between the two static sites and the backend
  (CORS, cross-origin cookies-less JWT auth) under Render's actual
  `onrender.com` domains rather than `localhost`.
- The M7 load gate (`docs/OPEN_DECISIONS.md` #12) against real Render
  infrastructure — this was never resolved even in the local dev
  environment; a single-instance Render Starter web service is unlikely
  to be a stronger substrate for it than the dev Docker container was.

If any of the above breaks on first deploy, that's expected risk this
document flagged rather than hid — fix forward and, if the fix is
non-obvious, consider it worth its own ADR.
