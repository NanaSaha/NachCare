# ADR-0006: `webpush` gem + OpenSSL 3.0 incompatibility

**Status:** Accepted
**Date:** 2026-08-03

## Context

The `webpush` gem (1.1.0, latest as of this build) generates and loads VAPID
EC keys by constructing an empty `OpenSSL::PKey::EC` and then mutating it
via `curve.private_key = ...` / `curve.public_key = ...`
(`lib/webpush/vapid_key.rb`). OpenSSL 3.0 (shipped with the `ruby:3.3-slim`
image's Debian trixie base, via `ruby:3.3.12`) made `PKey` objects immutable
after construction — this pattern raises `OpenSSL::PKey::PKeyError: pkeys
are immutable on OpenSSL 3.0` on **both** key generation (`Webpush.
generate_key`) and, critically, on every send (`Webpush.payload_send`,
which reconstructs a `VapidKey` from the stored public/private strings to
sign the VAPID JWT). This is a known, currently-unpatched gem/OpenSSL
version mismatch, not a bug in this codebase.

VAPID keys for local dev were generated by hand via raw `OpenSSL::PKey::EC`
(no gem helper), which works fine — key *generation* isn't the blocked
path, only the gem's specific mutate-after-construct pattern.

## Decision

`Domain::Notifications::Adapters::WebPushAdapter` calls `Webpush.
payload_send` but treats **any** exception from it (not just `Webpush::
InvalidSubscription`/`ExpiredSubscription`) as a delivery failure, returning
`false` rather than raising. This is correct behavior independent of this
specific bug — real push delivery legitimately fails for expired
subscriptions, unreachable push services, etc., and the fallback chain
(push -> SMS on red, unconfirmed) needs to treat all of those uniformly.
Fallback-chain specs stub the adapter boundary directly (not real crypto)
so the orchestration logic is tested deterministically regardless of
whether the underlying gem call succeeds in a given environment.

## Consequences

Real push delivery will not work in this dev container until the `webpush`
gem ships an OpenSSL 3–compatible release (or the adapter is rewritten
against a maintained alternative / hand-rolled RFC 8291/8292
implementation). Tracked here rather than in `docs/OPEN_DECISIONS.md`
since it's a pure engineering/tooling issue (R9), not a legal/clinical one
— revisit before relying on push delivery in a real deployment.
